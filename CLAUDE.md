- Alway use just to run command inside the container (just uv, just manage, just bash)
- The sprites works as this: you need to create a svg without comment in the sprites/ folder, then run "just sprites" to generate the all-sprites.svg. Once done you can use the tag "sprite" in the template to use it.
- Everytime you alter sprites, please run "just sprites" to update the all-sprites.svg
- When you create a new view, try to use a class and one of the one provided by django (FormView, ListView, CreateView, UpdateView, etc) to avoid boilerplate code.
- Every environment variable read by the Django settings must also be added to the `&django-environment` anchor in docker-compose.yaml (as `- VAR=${VAR:-<default>}`, matching the settings default) and documented in the "Environment variables" table in README.md (name, default, description). In production only the variables listed in the anchor reach the containers: the host .env is used by docker-compose solely for `${...}` interpolation and is not mounted into the containers, so `load_dotenv()` finds nothing there. Use the `:-default` form, because a bare `${VAR}` injects an empty string when unset, which overrides the default in settings.

## Batch actions
- Framework in `task_processor/batch.py`: one `BatchActions` subclass per model (registered in `BATCH_REGISTRY` via `@register_batch_actions`), one `@batch_action`-decorated method per action carrying its metadata (label, sprite, `form_class` as lazy string path, `applicable` queryset filter, `impact` preview sentence, position). One generic `BatchActionView` serves them all at `batch/<model>/<action>/` (POST preview → POST confirm), with the generic modal `templates/batch/_modal.html`, the bar partial `templates/partials/batch_bar.html` and `frontend/js/batch.js` (select mode, Gmail-style select-all).
- Selections are stateless and rebuilt server-side from the POST payload: explicit `ids`, or `select_all=1` + `q` (re-run through `apply_search`) minus `excluded_ids`. Ownership is always enforced by `BatchActions.base_queryset()`.
- Applicability and preview counts MUST be queryset filters / aggregate queries, never per-item Python over the selection — a select-all can cover thousands of rows. FSM transitions declare the SQL twin of their python `conditions` with `@batchable(filter_q=lambda: Q(...))` next to the transition in `models/item.py` (`@batchable(enabled=False)` excludes one from batch).
- Batch status changes (the "Move" action) execute through `item.flow.<method>()` per item, so FSM guards (`can_proceed`) and `post_save` signals (reminder/rrule clearing on completion) behave exactly like single-item transitions. Form-based transitions (`@requires_form`) are excluded from batch.
- `@batch_action` vs `@batchable` are different layers, don't conflate them. `@batch_action` (in `batch.py`) defines a *standalone* action: its own button in the bar and its own confirm modal, where `label`/`description`/`impact`/`applicable` all render (via `templates/batch/_preview.html`) — and this happens whether or not the action has a `form_class` (form-less actions still POST-preview then POST-confirm). `@batchable` (in `models/item.py`) only tunes how a form-less FSM transition behaves *inside the shared "Move" action*: form-less transitions are auto-pooled into Move's dropdown, and per-transition the ONLY thing surfaced is the affected count in the option label (`"Move back to Inbox (N)"`), computed from `filter_q`. A transition has no per-transition description/impact — those belong to the `move` action as a whole. So to give one transition its own description + affected-count preview, promote it to a dedicated `@batch_action` (like "Convert to reference") and add `@batchable(enabled=False)` so it isn't also duplicated in Move.
- Batch-action forms extend `BatchActionForm`; the view passes `user` (scope choices to the owner) and `selection` (the resolved queryset, for selection-aware choices like per-transition counts).
